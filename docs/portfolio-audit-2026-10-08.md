**Почему это подтвержденные замечания**

1. `git ls-files --error-unmatch backend/uv.lock` подтверждает, что файл отсутствует в индексе; `git check-ignore` указывает на правило `uv.lock`. В CI два job выполняют `uv sync --locked`. Эта команда завершает работу с ошибкой при отсутствующем lockfile — см. [официальную документацию uv](https://docs.astral.sh/uv/reference/cli/). Сам GitHub Actions в ходе проверки не запускался.

2. При вызове production-функции `decide_sync_item()` с существующей собственной записью, совпадающей версией и пустыми наборами разрешенных FK получены результаты:

   ```text
   foreign_skill      → updated, reason=None
   mood_score=99      → updated, reason=None
   empty_ciphertext   → updated, reason=None
   goal_change_only   → duplicate, reason=None
   ```

   Функция возвращает `updated` раньше `validate_incoming()` и `validate_refs()`. Затем endpoint использует переданные FK при обновлении. Это позволяет обойти проверку владельца связанной сущности при знании ее UUID; доступ к ее plaintext этим экспериментом не доказан. Для неверных числовых значений ограничение БД может вместо per-item rejection привести к откату batch: UPDATE находится вне savepoint и его IntegrityError здесь не обработан. Последствие для PostgreSQL требует отдельного live regression-теста.

3. `RegisterRequest` принимает пароль из 40 кириллических символов: это 80 UTF-8 байт. Вызов функции endpoint регистрации с таким payload воспроизводит необработанный `ValueError` в `hash_password()` еще до операций с БД. При обычной HTTP-обработке это означает серверную ошибку вместо понятного отказа. Проверен bcrypt 5.0.0, который также записан в локальном `uv.lock`; изменение поведения описано в [официальном changelog bcrypt](https://github.com/pyca/bcrypt). Смена алгоритма хеширования — отдельная задача совместимости существующих аккаунтов.

4. Записи вида `5433:5432` по умолчанию публикуют порт на всех host interfaces. Это противоречит заявленному локальному профилю; фактическая доступность зависит также от сети и настроек хоста. См. [документацию Docker](https://docs.docker.com/engine/network/port-publishing).

5. В audit присутствуют Vite/Tailwind и их зависимости, а также пакеты React Router. Часть findings относится к инструментам разработки и специфическим режимам вроде SSR, которых проект может не использовать. Числа audit описывают предупреждения по пакетам, а не 15 доказанных способов атаковать приложение. Например, [advisory esbuild](https://github.com/advisories/GHSA-67mh-4wv8-2f99) касается dev server. Разбор особенно уместен вместе с исправлением публикации dev-портов.

6. Пропуск `goal_id` уже явно отмечен в коде и закреплен тестом `frontend/src/db/toEntryPayload.test.ts`. В архитектуре обещана привязка `GOAL_UPDATE` к цели, но agent commit тоже не передает `goal_id`. Исправления одного сериализатора недостаточно. Альтернатива для более узкого MVP — явно убрать обещание этой связи из демонстрации до завершения функции.

**Практический порядок работ**

1. **Надежность:** lockfile/CI, UPDATE validation и FK ownership, пароль, localhost binding, разбор audit. Проверить смешанные sync batches с неверными item и чужими связями.
2. **Завершенность MVP:** согласовать goal link или сузить заявленные возможности; зафиксировать реальные ограничения. Пройти регистрацию → запись → sync → refresh/unlock → delete/undo → export на чистом локальном стеке.
3. **Презентация:** короткий README, синтетический dataset, 3–5 скриншотов desktop/mobile, видео до 3 минут, LICENSE, актуальная архитектурная схема.
4. **Контроль публикации:** чистый checkout без существующих node_modules/.venv и БД, инструкции работают, CI зеленый, сканирование секретов текущего состояния и истории, release tag вроде `v0.1.0-mvp`.

Готовность оценивается простым критерием: проверяющий понимает проект по первому экрану README, запускает его по инструкции, видит содержательный сценарий без чужого API key и может изучить тесты сложных решений. При выполнении этих условий MVP уже достаточно для сильной презентации.
