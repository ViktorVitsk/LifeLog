# LifeLog: отчёт о подготовке экспериментального MVP к портфолио

Дата: 9 октября 2026 года. Исходная ревизия: `a974fd0`; исходный [аудит](portfolio-audit-2026-10-08.md) сохранён как исторический документ.

**Вывод:** LifeLog подготовлен для показа как самостоятельный AI-assisted Fullstack/AI MVP. Основные подтверждённые дефекты исправлены, запуск на host stack воспроизводится, есть вымышленная демонстрация без платной модели. Это не заключение о готовности к публичной эксплуатации с чувствительными данными. Репозиторий не публиковался, push не выполнялся.

## 1. Исправленные ошибки

- **UPDATE через sync:** изменяемая запись проходит проверку диапазонов, конечности чисел, timestamp/timezone, непустого ciphertext и принадлежности skill/habit/context/goal. Чужие ссылки получают per-item rejection; валидные соседи продолжают сохраняться.
- **Конкурентные записи и частичные отказы:** UPDATE/DELETE сравнивают именно переданную версию в SQL, с owner и признаком живой записи. DELETE увеличивает версию; отсутствие версии для живой записи — конфликт. UPDATE выполняется в savepoint, нарушение DB constraint не отменяет пакет.
- **Гонка INSERT:** обнаруженный при повторном чтении изменённый payload больше не получает ложное `updated`, если UPDATE не выполнялся. Идентичный повтор получает `duplicate` с серверной версией.
- **Длинные пароли:** регистрация отвергает ввод свыше 72 UTF-8 байт понятной ошибкой вместо bcrypt 500. Вход в старые аккаунты сохраняет историческое bcrypt-поведение первых 72 байт. KEK выводится из полного исходного пароля; соли, KDF и содержимое старых аккаунтов не изменялись.
- **Связь с целью:** goal_id сохраняется через tool schema → normalisation → выбор существующей цели → подтверждение → encryption/enqueue → outbox payload → сервер и fingerprint. Неизвестная цель блокирует сохранение. Новая offline-цель отправляется перед зависимой записью при отсутствии обратной зависимости.
- **Устаревшая расшифровка:** кеш теперь различает содержимое ciphertext, а не только длину/ID. Правка той же длины обновляет показанный текст; ошибка расшифровки и удаление убирают прежний plaintext.
- **Воспроизводимость:** uv.lock включён в Git; Dockerfiles и Compose используют locked installs; backend virtualenv вынесен из bind mount. Ошибка миграции останавливает startup. CI дополнен production build и браузерным сценарием на временном PostgreSQL.
- **Локальный профиль:** все опубликованные Compose-порты привязаны к 127.0.0.1; Vite по умолчанию слушает loopback. Контейнерный Vite доступен через локально опубликованный порт.
- **Зависимости:** адресно обновлены применимые frontend/backend зависимости, без audit fix --force и без переписывания архитектуры. [Разбор оставшихся advisories](security-dependencies.md).

Backend-регрессии проходят через настоящий FastAPI endpoint и PostgreSQL. В тесте гонок контролируется момент появления конкурентной транзакции; mock не заменяет SQL и savepoints. Покрыты неверные метрики/пустой ciphertext/naive timestamp, чужие FK/ID, mixed batch, stale/missing version, удаление, идемпотентный повтор, гонки UPDATE/DELETE/INSERT и откат только одного constraint-failed item. Password-тесты проверяют HTTP-валидацию и login endpoint, совместимость старого хеша и отсутствие изменения KDF/salt.

Frontend goal-регрессия использует настоящий путь подтверждения/шифрования/IndexedDB/claim/toEntryPayload, включая запрет неизвестной цели. Браузерный demo-тест регистрирует fresh account, создаёт 16 зашифрованных fixture entries и цель, сохраняет ручную запись offline, синхронизирует, повторно входит и расшифровывает, обновляет до версии 2, экспортирует 17 записей без decrypt failures и удаляет ручную запись. Внешние HTTP-запросы блокируются и их число проверяется равным нулю.

Для UPDATE/DELETE дневниковой записи этот E2E вызывает реальные клиентские модули из браузера: полноценного Timeline edit/delete UI ещё нет. Это проверка фактического data path, а не заявление о наличии недостающего интерфейса. Вход, ручная форма, offline save и export проверены через UI. Первый вариант теста корректировался для обязательной разблокировки KEK после reload и ожидания штатного цикла sync; первоначальные неуспешные прогоны не выдаются за успешные.

## 3. Оставшиеся ограничения

- Docker/Compose и целевой PostgreSQL 16 нужно подтвердить отдельно; после публикации следует посмотреть первый CI run. Воспроизводимость host stack подтверждена, контейнерная — пока нет.
- npm всё ещё сообщает 9 затронутых пакетов. Часть относится к доверенным build-globs/CSS, часть — к неиспользуемым SSR/произвольным redirect-путям. Python-аудит сохраняет upstream critical advisory python-jose и timing advisory python-ecdsa; текущий HS256/явный allowlist не использует описанные уязвимые режимы. Это оценка применимости, не «нулевой риск». До public hosting или изменения JWT/SSR/build input нужен новый review.
- Hybrid encryption доверяет auth API и доставленному JavaScript: login password одновременно используется для KEK, а метрики, связи, теги и часть названий открыты. XSS/скомпрометированный клиент остаётся существенным риском. Независимого security-аудита нет.
- KDF v1 оставлен на 100k ради совместимости. Его усиление/отдельный encryption secret требует спроектированной миграции. Пароль нельзя безопасно заменить одной настройкой.
- Нет forgotten-password recovery, общего backup import/restore и доказанной процедуры восстановления. Экспорт полезен для доступа к данным, но plaintext-файл требует защиты; chat export ограничен этим устройством.
- IndexedDB не является резервной копией; eviction/очистка браузера может уничтожить несинхронизированное. Нет PWA/первой загрузки offline. Синхронизация может ждать очередного цикла, а не выполняться немедленно после каждого события.
- Циклическое создание новой цели и той же новой записи с взаимными ссылками не является атомарной graph transaction. Сначала синхронизируйте цель, затем связывайте progress entry. Чужие/неизвестные связи отвергаются.
- General Timeline edit/delete UI, уменьшение bundle, распределённый throttle и JWT revoke list остаются за рамками подготовки. Локальный single-process профиль сохранён.
- Интеграции с настоящими моделями/распознаванием речи и полный визуальный/accessibility аудит не проверены. Synthetic не доказывает качество модельного анализа.

Дальнейшая работа сейчас полезнее как отдельные небольшие итерации. Она не нужна для честного показа экспериментального MVP и не выполнялась ради увеличения числа возможностей.

## 5. Проверка публикации и истории

Проверяется вся достижимая история `git --all`, а не только HEAD. До этой подготовки было 73 коммита / 727 уникальных file blobs. Использован Gitleaks 8.30.1 с полной редактировкой значений, затем дополнительная проверка всех исторических blobs/путей и текущих публикуемых файлов на ключи, email/phone-like значения, локальные пути и случайные data exports/dumps. Положительные значения не выводились в отчёт.

**Секреты, токены, приватные ключи и случайно сохранённые дневниковые записи не обнаружены проверенными способами.** Базы, dumps, приватный .env и пользовательские exports не найдены среди исторических data-file кандидатов. Дополнительный Gitleaks-прогон новых коммитов и всех 269 публикуемых файлов также завершился с 0 findings. Это поиск свидетельств утечки, не математическое доказательство их отсутствия.

В истории **сохранены имена/email авторов и committer metadata**, а в старых технических заметках — локальные machine paths. Такие сведения будут видны при публикации всей истории. Значения здесь не раскрываются; владелец должен решить, допустима ли их публичность. Из актуальных документов дубли путей убраны. История не переписана, credentials не отзывались. Новые локальные коммиты подписаны нейтрально `Codex <codex@local.invalid>`, так как identity этой рабочей копии не была настроена; глобальные настройки не изменялись.

Не найдено оснований для обязательного отзыва секретов/очистки истории. Если владелец хочет убрать старую identity или пути, это отдельное решение перед push, требующее явного разрешения на изменение истории. Публиковать нужно Git checkout; локальные игнорируемые .env, базы и exports не должны попасть в архив, приложенный вручную.

## 7. Готовность к портфолио

**Да, как экспериментальный MVP с указанными ограничениями.** Проект демонстрирует содержательную работу с account/session state, клиентским шифрованием, revisions/outbox, частичными отказами, PostgreSQL concurrency и управляемыми AI-предложениями. Есть воспроизводимая демонстрация без личных данных/платного API, а README не преувеличивает статус или авторство.

Перед публикацией: решение владельца о видимости исторических identity/paths; выбор лицензии желателен, но отсутствие лицензии не мешает технически показать исходники; отдельный Docker/CI прогон подтвердит пока непроверенную часть. Публичный production-сервис с чувствительными данными — другая задача, требующая отдельной подготовки.

Push и публикация ожидают явного разрешения владельца.
